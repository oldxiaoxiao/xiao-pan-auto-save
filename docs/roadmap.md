# Compose 与客户端：差异和后续路线

[项目首页](../README.md) · [客户端指南](desktop.md) · [开发手册](development.md)

## 共用架构

```text
Compose：浏览器 → FastAPI → 追更/转存/下载/通知 → 网盘 + SQLite
客户端：原生 WebView 窗口 → 本机 FastAPI → 同一业务层 → 网盘 + SQLite
```

共享 `backend/` 与 `frontend/`，桌面层只管理原生窗口、本地服务、数据路径和进程生命周期。网盘协议、任务状态和下载历史只维护一套，避免两个版本逐渐出现行为差异。

## 当前版本差异

| 维度 | Compose / Web | Windows / macOS 客户端 |
|---|---|---|
| 运行位置 | 服务器、NAS 或本机容器 | 当前电脑 |
| 安装依赖 | Docker 与 Compose | 已打包 Python；使用系统 WebView |
| 界面 | 浏览器访问固定地址 | 原生窗口访问随机本机地址 |
| 调度持续性 | 容器和主机运行时持续执行 | 程序打开、电脑唤醒时执行 |
| 数据 | 挂载的 `./data` | 系统用户数据目录 |
| 默认下载 | 宿主机映射的容器目录 | 电脑用户数据中的 downloads |
| Aria2 | 可选 Compose profile | 不自带，可接已有 RPC |
| 浏览器脚本/远程 API | 固定地址，适合长期接入 | 随机端口，不提供稳定接入入口 |
| 管理鉴权 | 可配置密码和外部 Token | 自动生成本机凭证和会话 |
| 备份/迁移 | 备份挂载数据 | 备份用户数据目录 |
| 升级 | 更换版本化镜像并保留挂载 | 替换程序并保留用户数据 |
| 分发 | Linux amd64/arm64 镜像 | Windows x64、macOS arm64/x64 ZIP |

“下载到本地”指后端运行机器的磁盘，不是打开网页那台电脑。客户端和容器默认不共享数据库；把两个实例对准同一任务会产生重复执行风险。

## 0.1.1 / 0.2.0 已纳入的准备工作

- 0.1.1：统一版本号，密码实际保护管理 API，静态文件不能越过前端目录；Compose 默认绑定本机、持久数据挂载、排除私人构建上下文、锁文件安装和发行工作流；桌面随机本地端口、一次性凭证、系统数据目录、单实例锁、启动失败提示和退出清理；Windows 下载名称可移植处理；默认下载目录跟随数据目录；三平台原生编译、冻结后服务冒烟、发布附件校验和及专题文档。
- 0.2.0（主题「可信」）：总览仪表盘、命名模板库、脱敏备份恢复、凭据本地加密、账号到期预警、任务健康度与失败归因、通知分级与免打扰、磁盘/配额预检与限流退避、账号容灾切换、下载断点续传（含重启恢复）、对话式助手增强。

具体成功执行的检查以[验收记录](verification-0.1.1.md)、[发布说明](release-notes-0.2.0.md)和 GitHub 工作流为准。

## 后续执行顺序

### 1. 三端运行稳定性

v0.2.0 已交付客户端退出/重启后的下载恢复（断点续传 + 在途落库）。剩余优先项：休眠唤醒、网络切换、磁盘空间不足提示与长路径处理；建立 Windows 和两种 Mac 的 GUI 冒烟及升级回归。验收标准：保留数据升级，失效 Cookie/断网有可理解错误，客户端关闭不留服务进程。

### 2. 客户端常驻体验

增加托盘、“关闭窗口”和“退出程序”的明确区分、开机启动、原生目录选择、打开文件所在目录、桌面通知。验收标准：关闭窗口继续调度，退出确实停止，不因自启生成第二实例。

### 3. 正式分发与更新

Windows 安装器/签名、macOS 签名与公证、版本检测、下载校验、备份后升级和失败回退；是否启用自动更新由用户选择。验收标准：校验失败不能安装，升级后账号/任务/历史和下载目录保留。

### 4. 远程连接模式

客户端可选择连接已有 Compose 服务，明确显示运行机器、下载落盘位置与当前连接状态。需要抽离前端 API base URL、会话/SSE 连接、TLS 和远程授权。验收标准：不会误把服务器路径作为电脑路径，不会因多个 UI 创建多个调度器。

### 5. 网盘扩展与集成验证

按驱动接口逐个完成新网盘，实现解析、浏览、转存、建目录及声明能力后才标为支持。公开搜索源允许替换；通知与 Emby 建立受控服务测试。未完成闭环的驱动继续保持 `supported=False`。

## 桌面方案选择

0.1.1 使用 pywebview 与 PyInstaller，适合保留已有 Python 后端并尽快交付。后续若系统集成和更新需求显著增加，可评估 Tauri + Python sidecar，但不为了换壳重写业务层；Tauri 同样需要按平台打包 Python 服务。[pywebview 打包](https://pywebview.flowrl.com/guide/freezing.html)、[Tauri sidecar](https://v2.tauri.app/develop/sidecar/)。
