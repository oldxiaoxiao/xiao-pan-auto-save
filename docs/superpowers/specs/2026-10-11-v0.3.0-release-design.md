# v0.3.0 设计：客户端双版本分发（随包 aria2c）与常驻体验

> 主题：**开箱即用**。把「客户端用户还得自己装 aria2c」这件事彻底收掉，同时让客户端像个常驻程序而不是一个窗口。

## 1. 目标

1. **桌面客户端拆成两个变体**：`full`（随包自带 aria2c，解压即用）与 `slim`（不随包，沿用一键安装 / 接已有 RPC）。用户按自己情况二选一，不再被"自己去下载 aria2c"劝退。
2. **随包 aria2c 后真正做到零配置**：选 aria2 模式 → 程序直接拉起随包的 aria2c → 高速下载，全程离线、无需联网下载、无需理解 RPC。
3. **客户端常驻体验**：托盘常驻、"关闭窗口"与"退出程序"语义分离、开机自启、桌面通知。
4. **分发可信基础**：版本检测 + 下载校验 + 升级前自动备份（签名/公证按证书情况列为条件项）。

成功标准：

- `full` 包在**完全离线**的机器上，选 aria2 模式可直接下载成功，设置页显示「已检测到 aria2c（随包自带）」。
- `slim` 包行为与 0.2.1 完全一致，不因新增变体回退。
- 两个变体共用同一份代码，只差打包产物的二进制内容。
- 关闭窗口后调度继续；退出程序后无残留服务进程。

## 2. 非目标（本期明确不做）

- **不改动 aria2 协议与投递逻辑**：v0.2.1 已定的预检、账本、降级语义保持不变，本期只解决"二进制从哪来"。
- **不做 Linux 桌面包**：桌面端仍只出 Windows x64、macOS arm64/x64；Linux 走 Compose（aria2 由 compose profile 提供）。
- **不做远程连接模式**（连接已有 Compose 服务）：仍属 v0.4。
- **不做新网盘驱动**：网盘扩展按 roadmap 第 5 项独立排期。
- **不做自动更新的强制执行**：是否更新永远由用户点确认，不做静默替换。
- **FR-11（SQLite WAL 与写保护）**：继续顺延 v0.4，本期仅在 8.x 记录与 WAL 的衔接约束。

## 3. 现状与关键事实（决定了设计形状）

- `backend/services/aria2_manager.py` 的 `find_binary()` 已按 **随包自带 → 一键安装目录 → PATH → 常见路径** 的顺序查找，`bundled_dir()` 在冻结态读 `sys._MEIPASS/aria2`、源码态读 `assets/aria2`。**运行时侧已为随包预留好接口，本期只需把二进制放进去。**
- `ensure_running()` 已能在 RPC 不通时 spawn 带 RPC 的 aria2c（只听 `127.0.0.1`，未配地址用 `127.0.0.1:6800`）。随包后这条路径从"有条件可用"变成"必然可用"。
- `install()` 目前是 Windows 下载官方包 / macOS brew / Linux 包管理器——`full` 变体下它变成兜底（几乎不会被用到），`slim` 变体下仍是主路径。
- `scripts/build_desktop.py` 只支持 win32/darwin，产物名 `xiao-pan-auto-save-{ver}-{os}-{arch}.zip`；macOS 用 `ditto` 打 `.app`，Windows 用 `zipfile`。
- `desktop.spec` 当前 `binaries=[]`，`datas` 收 `frontend/dist`、`LICENSE`、`docs/desktop.md`、`tzdata`。
- `release.yml` 的 desktop 是单维矩阵 `runner: [windows-latest, macos-14, macos-15-intel]`，产物 `desktop-${{ matrix.runner }}`，publish 用 `pattern: desktop-*` + `merge-multiple` 汇总。
- **发布流水线会校验 tag 必须等于 `v$VERSION`**（取自 `backend.__version__`），变体不得引入第二个版本号。
- macOS 官方**不提供** aria2 二进制（只有源码 + Windows 包）——这是本期最大的工程不确定点，见 4.2 与第 8 节。

## 4. 设计

### 4.1 两个变体的定义

| 变体 | 标识 | 随包内容 | 产物命名 | 适合谁 |
|---|---|---|---|---|
| 完整版 | `full` | `aria2c` 可执行文件及其依赖库 | `xiao-pan-auto-save-{ver}-{os}-{arch}-aria2.zip` | 绝大多数用户，尤其客户端用户：解压即用、离线可用 |
| 精简版 | `slim` | 无 | `xiao-pan-auto-save-{ver}-{os}-{arch}.zip`（沿用现名） | 已有自己的 aria2、在意体积、或不希望随包 GPL 二进制的用户 |

- **推荐默认下载 `full`**，发布说明里把两者区别讲清楚；`slim` 保留现名以维持既有链接/习惯连续。
- 两者**代码完全一致**，差异仅在打包阶段是否把 `assets/aria2/` 打进产物；因此行为差异可用同一套测试覆盖，只多一条"随包二进制可执行"的打包期校验。
- 变体标识只存在于**构建期与文件名**，不进数据库、不进设置项——避免"同一份数据目录换包后行为漂移"。

### 4.2 二进制来源与合规

**Windows x64**：aria2 官方 GitHub Release 提供 `aria2-1.37.0-win-64bit-build1.zip`（内含 `aria2c.exe`，基本自包含）。构建期下载 → 校验 → 取出 `aria2c.exe` 放入 `assets/aria2/`。与现有 `install()` 用的是同一个地址，行为一致。

**macOS（arm64 / x64）**：官方无二进制，采用 **brew bottle + 依赖重定位**：

```bash
brew install aria2
mkdir -p assets/aria2
cp "$(which aria2c)" assets/aria2/aria2c
# 递归收敛：枚举非系统依赖，拷进同目录并改写为 @loader_path 相对引用
# otool -L 取依赖 → cp → install_name_tool -change ... @loader_path/<name>
# 直到二进制与其依赖都不再引用 /opt/homebrew
assets/aria2/aria2c --version   # 打包期必须跑通，否则构建失败
```

要点与已核实事实（本机 `brew` 实测，2026-10-11）：

- **aria2 1.37.0 是 bottled**：`brew info aria2` 显示 `stable 1.37.0 (bottled)`，bottle 1.7MB、安装后 5.8MB。runner 上 `brew install aria2` 走预编译包，**不会退化成源码编译**，构建耗时可控。
- **需要重定位的依赖**：`brew deps aria2` 给出 c-ares、ca-certificates、gettext、json-c、libssh2、libunistring、openssl@4、readline、sqlite。真正的链接项以 `otool -L` 为准（该命令本身会提示声明依赖 ≠ 实际运行时依赖），但量级在 6~9 个 dylib。
- 必须**递归**收敛（被拷进来的 dylib 自身也依赖 brew 库）；只拷主二进制会在目标机直接 `dyld: Library not loaded`。构建期 `--version` 校验是这道工序的兜底。

**合规**：aria2 为 **GPL-2.0-or-later**（brew 公式明示 `License: GPL-2.0-or-later`，已核实），本项目为 AGPL-3.0-only。随包分发必须：
- 在包内附 aria2 的 `COPYING`/许可证文件；
- 在 `docs/desktop.md` 与发布说明里给出源码获取途径与书面要约；
- `slim` 变体的存在本身也是对"不愿随包 GPL 二进制"这一诉求的正面回应。

### 4.3 打包接线

**`desktop.spec`**：把 `assets/aria2` 下的内容作为二进制收进包，落在 `_MEIPASS/aria2/`（与 `bundled_dir()` 约定一致）。目录不存在时静默跳过，`slim` 变体因此天然不产出该目录：

```python
aria2_dir = root / "assets" / "aria2"
if aria2_dir.is_dir():
    for path in sorted(aria2_dir.rglob("*")):
        if path.is_file():
            a.binaries.append((str(path.relative_to(aria2_dir)), str(path), "BINARY"))
```

**`scripts/build_desktop.py`**：新增 `--variant {full,slim}`（默认 `slim`，保持向后兼容）。
- `full` 时先调用预置脚本把二进制准备好（失败即 `SystemExit`，绝不出半成品包），再做一次 `aria2c --version` 校验；
- 产物名按变体加后缀 `-aria2`；
- 冒烟测试（`--smoke-test`）保持不变，`full` 变体额外可选做一次"起 RPC → ping → 停"的集成冒烟。

**`.github/workflows/release.yml`**：矩阵加一维，产物名与归档都要带变体，否则 publish 汇总时会互相覆盖：

```yaml
matrix:
  runner: [windows-latest, macos-14, macos-15-intel]
  variant: [slim, full]
name: desktop-${{ matrix.runner }}-${{ matrix.variant }}
# - run: python scripts/build_desktop.py --variant ${{ matrix.variant }}
```

代价：桌面构建任务由 3 个变 6 个，构建时长与存储翻倍——已知并接受。

### 4.4 运行时：发现、自动启动、状态呈现

运行时**几乎零改动**，这是本设计的要点：

- `find_binary()` 已优先读随包目录，`full` 变体直接返回 `source="bundled"`。
- 设置页已有的 `SOURCE_TEXT` 映射会把 `bundled` 显示成 **「随包自带」**，`slim` 显示「未检测到 aria2c」并给出「一键安装」按钮。`full` 因 `installed=true` 自动隐藏安装按钮——**无需新增 UI 分支**。
- 自动启动逻辑（`ensure_running`）不变：随包二进制让它从"可能拉不起"变成"必然拉得起"。
- 需补的小改动：`full` 变体下若用户已配了远端 aria2 地址，**仍优先连远端**（现有逻辑已保证），随包二进制只在地址为本机或未填时使用。

### 4.5 客户端常驻体验（P1）

- **托盘常驻**：关闭窗口最小化到托盘，托盘菜单提供「打开界面 / 立即运行 / 退出」。
- **语义分离**：「关闭窗口」= 界面隐藏、调度继续；「退出程序」= 停止服务、清理 aria2 子进程与单实例锁。桌面端现有的 `atexit`/退出清理需覆盖"随包 aria2 是本进程拉起的才回收"这一约束。
- **开机自启**：Windows 用启动目录快捷方式或 Run 注册表项；macOS 用 LaunchAgent。默认关闭，设置页开关。必须保证不会因自启产生第二实例（复用现有单实例锁）。
- **桌面通知**：补一条原生通知通道，与既有 Web 通知并存，避免重复打扰（沿用分级：需处理 / 仅告知）。

### 4.6 分发与更新基础（P2）

- **版本检测**：启动时（或手动检查）比对 GitHub Release 的最新 tag 与本地 `backend.__version__`，只提示不强制。
- **下载校验**：下载后比对发布附件里的 `SHA256SUMS`，不符即拒绝安装并保留当前版本。
- **升级前备份**：替换程序前自动走一次"不含凭据"备份，失败即中止升级。
- **签名 / 公证**：Windows 签名与 macOS 签名+公证列为**条件项**——取决于证书是否到位。注意：一旦做签名，随包的 `aria2c` 及其 dylib 也**必须一并签名**，否则 macOS 公证会失败；这是把 4.2 与本节耦合起来的关键约束。

## 6. 测试与验收

**打包期（每个变体、每个平台）**

- `full`：`assets/aria2/aria2c --version` 必须成功（macOS 这道能拦住漏拷 dylib）。
- `full`：可选集成冒烟——起 RPC → `aria2.getVersion` → 停进程。
- `slim`：确认产物内**不含** `aria2/` 目录（防止误打包）。
- 冒烟测试 `--smoke-test` 保持通过。

**运行期**

- `full` 离线机器：模式选 aria2 → 下载成功 → 设置页显示「已检测到 aria2c（随包自带）」，引擎状态为 aria2。
- `full` 但用户填了远端地址：仍连远端，不在本机乱起随包 aria2。
- `slim` 无 aria2c：与 0.2.1 一致，给出「未找到 aria2c，可一键安装」。
- 退出程序后：随包拉起的 aria2 子进程被回收，无残留。

**既有回归**：全量后端测试 + 前端 lint/typecheck/build 保持通过；特别注意 `TZ=UTC` 下跑一次（0.2.1 修过的时段依赖用例）。

**人工验收（GUI 冒烟）**：Windows 与两种 Mac 各验一次——保留数据升级、托盘/退出语义、随包 aria2 实际下载一个大文件。

## 7. 分阶段交付

| 阶段 | 内容 | 可独立发版 |
|---|---|---|
| **S1（本期核心）** | 双变体分发 + 随包 aria2c（4.1–4.4） | 是，可单独作为 0.3.0 |
| S2 | 客户端常驻体验（4.5 托盘/语义/自启/通知） | 是 |
| S3 | 分发与更新基础（4.6 版本检测/校验/备份升级） | 是 |
| S4（条件） | 签名与公证（依赖证书，且需连带签署随包二进制） | 是 |

建议：S1 单独成版即可兑现"客户端免装 aria2c"这一核心价值；S2/S3 视精力并入或顺延。若 S1 就要带上 S2，注意 4.5 的退出清理必须覆盖随包 aria2 子进程。

## 8. 风险与开放问题

1. ~~**macOS 无官方二进制**~~ —— **已由 spike 验证关闭**（2026-10-11，run 38132681052）：
   `macos-14`(arm64) 与 `macos-15-intel`(x64) 的 `full` 变体**均构建成功**并通过 `aria2c --version`
   自检。brew + `otool`/`install_name_tool` 递归重定位那条路可行。
   中途踩到的坑：Windows full 因脚本中文日志在 cp1252 控制台抛 `UnicodeEncodeError` 而失败
   （首轮 spike 38132143342），已在 `main()` 重配 stdout/stderr 为 utf-8 修掉。
   结论：`full` 三平台全量铺开，不需要退到"只给 Windows 出 full"。
2. **体积（spike 实测，zip 压缩后）**：macOS arm64 +1.97MB、macOS x64 +2.11MB、Windows x64 +2.45MB。
   远小于原先估的 15~25MB——aria2 主程序与 brew dylib 在 zip 里压缩率很高。
   发布说明按变体标注实际体积即可，无需为此纠结"是否值得随包"。
3. **许可**：随包 GPL-2.0-or-later 二进制的源码要约与许可证附带必须落实，否则不该出 `full`。
4. **签名耦合**：将来做签名/公证时必须连带签署随包二进制（macOS 尤其严格），4.6 与 4.2 存在顺序依赖。
5. **构建成本**：桌面任务 3 → 6，CI 时长与缓存压力翻倍。
6. **开放问题**：`full` 是否要默认勾选 aria2 模式？倾向**不默认**（仍由用户选模式），只在用户选了 aria2 时静默拉起随包二进制——保持"不替用户做决定"的既有原则。
7. **开放问题**：随包 aria2c 的版本如何升级？建议绑定发版（每次发版重新取最新稳定版），并在发布说明里写明内置版本。
