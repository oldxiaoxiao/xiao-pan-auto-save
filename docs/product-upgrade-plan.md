## 一、分析结论速览

0.1.1 是一个**工程完成度明显高于产品完成度**的版本：追更引擎、试跑一致性、下载账本、三端发行、鉴权这些都做得很扎实，测试约 380 例、交付物带 SHA256 与 GHCR 镜像，可信度基础是有的。

但产品侧存在三个结构性缺口：

1. **价值半径过窄**：驱动抽象层做完了，却只落地夸克一个网盘；8 个驱动骨架全部 `supported=False`。架构红利没有兑现成用户价值。
2. **"放着不管"还没被兑现**：这是自动追更类工具的核心承诺。目前 Cookie 过期、磁盘写满、链接失效、客户端退出这四类中断，都要用户自己去翻日志/下载页才能发现。
3. **没有"一眼看健康"的入口**：五个一级页面（任务/账号/设置/日志/下载），唯独没有总览。用户判断"我的追更是不是还好"，要在四个页面之间来回拼信息。

建议下一阶段用一条主线串起来：**v0.2 让它可信 → v0.3 让它好用 → v0.4 让它开放**。

## 二、现状盘点

### 2.1 产品定位

> 把网盘分享链接变成可管理的追更任务：按计划检查分享内容，只转存新增，按规则整理命名，按需落盘并推送结果。

技术栈 FastAPI + SQLite + Vue 3 + Element Plus，业务思路源于 [quark-auto-save](https://github.com/Cp0204/quark-auto-save)（AGPL-3.0，公开资料约 3k star），本项目重组了架构与管理界面（来源：项目 README；引用时间 2026-10-10）。

### 2.4 代码层面的产品化缺口（改造落点）

| 缺口                            | 代码落点                                                | 产品影响                    |
| ----------------------------- | --------------------------------------------------- | ----------------------- |
| 账号 Cookie 明文入库                | `backend/models.py` `account.cookie`                | 备份文件即凭据泄露面；无脱敏导出        |
| SQLite 无 WAL / 无 busy_timeout | `backend/database.py`                               | 并发写冲突与掉电损坏风险，备份窗口不安全    |
| 无总览/统计路由                      | `frontend/src/router.ts`（仅 5 个页面）；后端无统计端点           | 无健康度视角，无法复盘             |
| 无 i18n、无暗色主题                  | 无 i18n 目录；`theme.css` 无 dark 分支                     | 国际化与夜间使用受限              |
| 主 chunk 1.0M、CSS 360K         | `vite.config.ts` 无 `manualChunks`；Element Plus 全量引入 | 首屏加载慢，远程访问体感差           |
| 下载内存注册表非持久化                   | `core/download_registry.py`                         | 重启后在途作业失联，靠 24h 超时兜底判失败 |

## 三、六维诊断

| 维度     | 判断      | 主要问题                                                 |
| ------ | ------- | ---------------------------------------------------- |
| A 价值闭环 | 中       | 单网盘限定用户池；缺结果总览；缺内容元数据（TMDB 对齐），高阶整理仍靠外部工具            |
| B 可信可靠 | 弱（最大短板） | Cookie 失效、磁盘写满、链接失效、客户端退出四类中断均需用户自查；内置下载无断点续传；队列不持久化 |
| C 体验可用 | 中       | 无总览页；通知无分级（结果刷屏掩盖"要你处理"）；正则/魔法变量对小白门槛高；无暗色主题         |
| D 扩展生态 | 中（潜力最大） | 8 驱动未实现；无事件钩子/插件；无失效自动换源；媒体库集成仅 Emby                 |
| E 多端分发 | 弱       | 桌面"退出即停"与核心价值冲突；未签名公证；无远程模式；随机端口切断脚本接入               |
| F 运营增长 | 弱       | 无本地统计看板（无法自证价值）；缺上手引导与反馈闭环；迁移卖点未在首页曝光                |

**诊断排序（按对核心承诺的破坏程度）**：B > A > E > C > D > F。

## 四、目标用户与场景

> 以下画像基于项目文档与功能取向推导，属**工作假设**，非调研数据，需社区/Issue 验证后再固化。

| 角色                   | 场景                           | 核心目标           | 主要痛点                         | 熟练度 |
| -------------------- | ---------------------------- | -------------- | ---------------------------- | --- |
| P1 影音玩家（NAS/Compose） | 长期挂机，几十个追更任务，接 Emby/Jellyfin | 不打扰、不出错、自动到位   | 中断无人知；失效链接要手动换；多账号配额管理       | 熟练  |
| P2 追剧用户（桌面客户端）       | 个人电脑，3–10 个任务，只想"更新了就帮我存"    | 装上就忘，更新了正好在网盘里 | 关机/退出不跑；正则看不懂；通知看不懂          | 新手  |
| P3 资源整理者（多账号/批量）     | 多账号轮换、批量转存归档、脚本接入            | 批量、可控、可脚本化     | 配额满/风控后任务静默失败；批量操作弱；API 覆盖不全 | 专家  |

**主流程旅程（P1，痛点标注）**：部署 Compose → 填 Cookie → 建任务 → 试跑 → 启用追更 →（⚠️ 中途 Cookie 过期/链接失效，只有翻日志才知道）→ 下载落盘 →（⚠️ 磁盘写满后失败原因藏在下载页）→ Emby 刷新 →（⚠️ 想确认"这周有没有正常"只能逐页看）。

**P2 旅程断点更严重**：装客户端 → 建任务 → 关窗口（⚠️ 服务停止，追更停摆）→ 下次开机忘了开（⚠️ 漏更）。

## 五、升级路线：三期主题

### v0.2「可信」——让用户敢长期放着不管

目标指标（口径见第十节）：**追更中断自愈/自曝率 ≥90%**；因 Cookie 失效导致的静默失败归零；客户端重启后在途下载可恢复。

### v0.3「好用」——降低门槛，扩大用户池

目标：**新手 5 分钟建出第一个可跑任务**；第二个网盘可用；桌面端"退出即停"问题消除。

### v0.4「开放」——从工具走向平台

目标：事件/插件生态可用；媒体库集成覆盖主流；可选远程连接与家庭共享（只读角色）。

## 六、方案对比与选型

### 6.1 多网盘扩展（战略项）

| 方案                   | 思路                                | 成本                 | 风险                           | 体验      | 结论                    |
| -------------------- | --------------------------------- | ------------------ | ---------------------------- | ------- | --------------------- |
| A 逐个自研驱动             | 按 `drivers/base.py` 五原语逐个实现       | 高（每个 4–6 人周估算）     | 协议变更、风控                      | 最完整     | **推荐作为主线**，但先做 1 个样板  |
| B AList/WebDAV 中间层桥接 | 借 AList 已有网盘适配，本项目只对接一个"AList 驱动" | 中（3 人周估算）          | 依赖用户自部署 AList；能力受 AList 接口限制 | 覆盖广但深度浅 | **推荐作为并行快路径**，先解"有没有" |
| C 社区共建驱动 SDK         | 开放驱动规范 + CI 契约测试                  | 低（1.5 人周规范 + 评审成本） | 质量参差                         | 长期收益大   | 采纳，与 A 并行             |

**推荐**：B + C 先上（低成本快速扩大覆盖），A 选择性做 1 个深度样板（优先 115 或 123，按社区呼声与协议可得性二选一，需先做技术可行性验证）。**修正留痕**：原路线图第五节"按驱动接口逐个完成新网盘"调整为"B 先行 + A 单点突破"，原因是逐个自研周期过长，会持续压制用户池。

### 6.2 下载可靠性：断点续传

| 方案                         | 思路                           | 成本             | 结论                        |
| -------------------------- | ---------------------------- | -------------- | ------------------------- |

### 6.3 桌面常驻形态

| 方案                         | 思路                               | 成本          | 结论                            |
| -------------------------- | -------------------------------- | ----------- | ----------------------------- |
| A 继续 pywebview，补托盘/自启/关闭语义 | 改 `desktop/main.py`、`runtime.py` | 低（2.5 人周估算） | **推荐本期**：复用现有打包链路             |

| 方案            | 思路                       | 风险           | 结论         |

### FR-01 磁盘与配额运行预检（Must）

业务规则：

1. 下载开始前必须校验目标盘可用空间 ≥ 待下文件总大小 × 1.1，不足则跳过并生成"需处理"级通知，**禁止**写入半截文件后失败。
2. 转存前应该校验目标账号剩余容量；容量不足时标记任务并通知，不静默失败。
3. 网盘接口连续返回限流/风控响应时，必须指数退避（初始 60s，上限 30min）并暂停该账号的任务，**禁止**无限重试。
4. 阈值可在设置页配置，默认：磁盘预留 10% 或 5GB（取大者）。

验收标准：

- **Given** 目标盘剩余空间小于待下文件总大小 ×1.1，**When** 触发下载，**Then** 该下载不开始、账本记 `failed` 且 error 为"磁盘空间不足"，并推送"需处理"通知。
- **Given** 账号连续 3 次限流响应，**When** 下一次调度到达，**Then** 该账号任务跳过本轮，日志写明退避至的具体时间。

### FR-02 账号凭据到期预警（Must）

业务规则：

1. 系统必须按可配置周期（默认每日）检查账号有效性，复用 `account_info` 能力。
2. 检查失败/失效时：账号卡显示"需更新"徽标，并发送"需处理"级通知；相关任务**应该**继续保留但不空跑。
3. 禁止在列表页、日志、导出文件中输出完整 Cookie；只出掩码。

验收标准：

- **Given** 某账号 Cookie 已失效，**When** 每日检查执行后，**Then** 账号页该卡片显示"需更新"，通知渠道收到 1 条（且仅 1 条）"需处理"提醒，24h 内不重复骚扰。
- **Given** 用户在账号页重新粘贴 Cookie，**When** 保存成功，**Then** 徽标清除，相关任务下次调度恢复执行。


### FR-03 任务健康度与失败归因（Must）

业务规则：

1. 任务行必须显示健康状态：正常 / 待处理（失效链接、连续失败、账号异常）/ 已停摆。
2. 必须提供"待处理"筛选视图，聚合展示所有异常任务与最近失败原因（取最后一次运行日志的错误摘要）。
3. 连续失败阈值默认 3 次，可配置。
4. 失效分享（`shareurl_ban`）必须归入"待处理"并提供"重新验证链接"操作。

验收标准：

- **Given** 任务 A 连续 3 次运行结果为 `failed`，**When** 用户打开任务页，**Then** A 显示"待处理"徽标，并在"待处理"筛选中可见，附最近失败原因摘要。
- **Given** 用户点击"重新验证链接"且分享已恢复，**When** 验证通过，**Then** 徽标清除并计入下次调度。

### FR-04 通知分级与免打扰（Must）

业务规则：

1. 通知必须分两级：**需处理**（失效、凭据过期、磁盘/配额不足、重试用尽）与**仅告知**（转存成功摘要）。
2. 必须支持免打扰时段（默认 23:00–08:00）；"需处理"级在免打扰时段内**应该**聚合为次日 1 条摘要，而非丢弃。
3. "仅告知"级必须支持按任务维度关闭。

验收标准：

- **Given** 免打扰时段内产生 3 条"需处理"事件，**When** 免打扰结束，**Then** 收到 1 条聚合摘要，包含 3 条事件。
- **Given** 用户关闭任务 B 的"仅告知"，**When** B 转存成功，**Then** 不推送该类通知；B 失效时**仍**推送"需处理"。

### FR-05 备份 / 恢复与脱敏导出（Must）

业务规则：

1. 必须支持一键导出备份，提供"含凭据"与"不含凭据"两种；含凭据文件必须在界面明确警示并建议设置访问口令。
2. 恢复时必须校验版本兼容性，不兼容时拒绝并给出可读原因；恢复前必须自动备份当前数据。
3. 备份必须包含：任务、账号、设置（`setting` KV）、下载历史。

验收标准：

- **Given** 用户选择"不含凭据"导出，**When** 恢复该备份到新实例，**Then** 任务与设置完整恢复，账号行保留但标记为"需更新"，且备份文件中检索不到完整 Cookie 字符串。
- **Given** 备份文件版本高于当前程序，**When** 执行恢复，**Then** 拒绝并提示"备份来自更高版本，请先升级程序"。

### FR-06 账号容灾切换（Must）

业务规则：

1. 任务必须支持配置备用账号（有序列表）；主账号不可用（失效/配额满/风控）时自动切换下一个。
2. 切换必须落日志并通知（"仅告知"级）。
3. 所有候选账号均不可用时，任务标记"待处理"，**禁止**丢弃任务。
4. 切换后**禁止**改变任务的保存目录与命名规则。

验收标准：

- **Given** 任务绑定主账号 A 与备用账号 B，A 配额满，**When** 调度执行，**Then** 使用 B 完成转存，日志与通知记录"A 不可用，已切换 B"。
- **Given** A、B 均不可用，**When** 调度执行，**Then** 任务进入"待处理"，不删除、不置为停用。

### FR-07 下载队列持久化与断点续传（Must）

业务规则：

1. 在途下载必须落库（`download_record` + 新增的断点元数据），后端重启后自动恢复或明确标记。
2. 内置下载器必须支持基于 Range 的续传：记录已验证字节数，重启后从该位置继续；校验失败（远端文件变更）时整片重下并记录原因。
3. `.part` 文件在恢复时必须可识别并接管；不可接管时必须清理或改名留档，**禁止**留下不可解释的残留。
4. **禁止**恢复后产生同路径并发写入（沿用现有同路径守卫，扩展到恢复路径）。

验收标准：

- **Given** 一个 3GB 文件下载至 40% 时后端重启，**When** 服务恢复，**Then** 该作业继续从约 40% 位置下载，最终文件大小与远端一致，账本只有 1 条记录收口为 `done`。
- **Given** 远端文件在中断期间被替换，**When** 尝试续传校验失败，**Then** 触发整片重下并在账本标注原因。

### FR-08 凭据本地加密存储（Must，安全底线）

业务规则：

1. 账号 Cookie 必须加密存储；密钥来自本地数据目录的密钥文件（`600` 权限），**禁止**硬编码进代码或镜像。
2. 读取时解密注入驱动，内存中用完即弃；日志与 API 响应**禁止**输出明文。
3. 必须提供密钥丢失的明确提示路径（提示重新录入凭据，而非静默失败）。
4. 迁移期：启动时检测明文凭据并自动加密，升级路径不得中断已有任务。

验收标准：

- **Given** 数据库中存有凭据，**When** 直接读取 SQLite 文件，**Then** 检索不到明文 Cookie。
- **Given** 密钥文件被删除，**When** 服务启动，**Then** 明确提示"凭据无法解密，请重新录入"，且任务不因解密失败而崩溃。

### FR-09 总览仪表盘（Should，最小数据能力）

业务规则：

1. 提供"今日/近 7 天"视图：新增转存文件数、成功任务数/应跑任务数、待处理项数、下载完成量与失败量。
2. 必须提供"待处理"直达入口（跳转 FR-03 聚合视图）。
3. 所有指标必须可点击下钻到明细（任务/下载历史）。
4. 数据全部来自本地 SQLite，**禁止**任何外部上报。

验收标准：

- **Given** 近 7 天有 2 个任务失效、15 次成功转存，**When** 打开仪表盘，**Then** 显示"待处理 2 / 近 7 天新增 15"，点击"待处理 2"跳转至已筛选的待处理列表。

### FR-10 命名模板库与推荐预设（Should）

业务规则：

1. 提供内置模板（剧集 `SxxExx`、综艺按日期、动画连续编号、电影），一键套用正则 + 替换 + 变量组合。
2. 套用前必须经过试跑（复用现有 dry-run），试跑结果不通过时**应该**提示不匹配的样本文件名。
3. 允许保存为个人模板并复用。

验收标准：

- **Given** 新手用户选择"国产剧 SxxExx"模板，**When** 执行试跑，**Then** 预览中 `第01集.mp4` 被规范为可预期命名，且不匹配文件被单独列出。

### FR-11 SQLite 写保护（Should，技术底座 · 推迟至 v0.3/v0.4）

> **状态**：按用户决策，本项不在 v0.2 交付。替代方案：v0.2 的备份功能已采用一致性导出（`VACUUM`-style 快照）而非高峰期直接复制 db 文件，规避了主要风险。FR-11 的完整 WAL / `busy_timeout` 改造随 v0.3「好用」或 v0.4 技术底座一并推进。

业务规则：启用 WAL、`busy_timeout` ≥5s、备份走 `VACUUM INTO` 或一致性快照；**禁止**在下载写入高峰期直接复制 db 文件作为备份。

验收标准：

- **Given** 下载进行中，**When** 执行备份，**Then** 产出的备份文件可被新实例完整打开且任务数一致。

### 本期明确不做（Won't）

- 不做 PT / 种子下载与站点体系（定位不同，避免与现有生态冲突）
- 不做在线播放、海报墙刮削（交给 Emby/Jellyfin/Plex 等专长工具）
- 不做账号共享、代存、托管服务（合规与安全风险）
- 不做强制云上报与任何用户数据外发
- 不做移动端原生 App（v0.3 前只做关键页面响应式适配）
- 不做静默自动换源（见 6.4 决策）

## 十、指标与最小数据能力

> 全部为**本地统计**，不依赖外部服务，不向任何服务端上报。

## 十三、关键假设（待确认，可推翻）

1. 目标用户以夸克网盘用户为主，且其中相当比例有第二网盘需求——**待社区 Issue / 投票验证**。
2. 桌面端用户占比不低于 30%（影响 FR-07 优先级）——**待发版下载数据验证**。
3. 用户愿意为"稳定"优先于"更多网盘"——需在 v0.2 发布说明中收集反馈。
4. 多账号容灾是 P3 用户强需求，而非小众诉求——**待验证**。
5. 凭据加密不引入云端密钥托管（自托管工具，用户掌控优先）——默认按此设计。
6. 项目不接受任何用户数据外发（含匿名统计）——默认按此设计，如与增长目标冲突需单独评审。
