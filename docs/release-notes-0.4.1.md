# 小盘自动转存 0.4.1 · 数据库不再怕"边写边备"

> FR-11 落地（从 v0.2 一路顺延的技术底座）：**启用 WAL、写冲突排队等待、备份改走一致性快照。**
>
> 它修的是一类最难受的缺陷：不出错、不报警，等你真要恢复时才发现备份少了一截。

## 为什么要做

默认日志模式下，写库会锁住整库：下载高峰一边写账本、一边刷界面列表，就是"写堵读"。
而备份此前是**直接复制 db 文件**——这在 WAL 模式下有个致命陷阱：尚未 checkpoint 的提交只在
`-wal` 文件里，复制主库会得到一份**能正常打开、但少了最后一批数据**的库。它不报错，
所以比"备份失败"更危险。

## 改了什么

| 项 | 之前 | 现在 |
|---|---|---|
| 日志模式 | 默认（rollback journal） | **WAL**：读写不再互堵 |
| 写冲突 | 立刻抛 `database is locked` | `busy_timeout = 5000ms`：排队等待而不是报错 |
| `synchronous` | 默认 FULL | **NORMAL**（WAL 下的官方推荐搭配） |
| 备份 | `shutil.copy2` 直接复制 db 文件 | **`VACUUM INTO` 一致性快照**；失败降级到官方 online backup API |

- WAL 在部分网络文件系统（NAS / 某些 SMB 挂载）上不受支持，SQLite 会拒绝切换。
  这种情况下**如实降级**并记一条 warn，绝不因为一个 pragma 让程序起不来。
- `GET /api/health` 多了 `db` 字段（`journal_mode`、`busy_timeout`）：WAL 到底开没开，
  当场就能查，不用翻日志猜。
- 两条一致性路径都失败（例如目标文件压根不是 SQLite 库）时，仍退化为文件复制保底，
  但会明确记 warn 说明"这份可能缺最近的提交"——保底拿点东西比什么都拿不到强，
  但不能把它当成可信备份。

## 验证

- 新增 8 例：WAL 生效、`busy_timeout ≥ 5s`、第二个写者排队而非报错、
  快照包含仍留在 `-wal` 里的提交、`VACUUM INTO` 不可用时走 backup API、失败不留半截文件。
- 后端：ruff 通过，**636 passed / 1 skipped**（较 0.4.0 +8）。
- 真机实测（真实 SQLite 3.50.4，非 mock）：造一个 WAL 库、关掉自动 checkpoint、提交 5 行后——

  | 方式 | 结果 |
  |---|---|
  | 文件复制（旧做法） | `no such table`：**整张表都不在副本里** |
  | 一致性快照（现在） | 5 行，完整 |

- 真实服务：`GET /api/health` 返回 `{"db":{"journal_mode":"wal","busy_timeout":5000}}`；
  `POST /api/update/prebackup` 正常落出快照。

## 升级注意

1. 升级后数据目录会多出 `xiao_pan.db-wal` 与 `xiao_pan.db-shm`，**属正常，不要手动删除**。
2. 本版未改动表结构，升级向下兼容；存量库会在首次连接时自动切到 WAL。
3. 备份（`backups/`）与导出（「设置 → 备份」）自此都是一致性快照，可放心在下载进行时执行。
4. 若把数据目录放在不支持 WAL 的网络盘上，性能与并发表现会退回旧模式，health 接口可查证。

## 已知边界（本期未做）

- **不做签名与公证**（产品决定，非待办）：这是开源个人工具，不采购代码签名证书与 Apple 开发者资质。
  校验靠发布包自带的 `SHA256SUMS`，信任靠源码公开。首次打开的系统拦截属预期行为，
  绕过步骤见[客户端指南](desktop.md)「为什么没有签名，被拦了怎么办」。
- 没有 Windows 安装器，也没有"下载后自动替换并重启"的能力。
- 仍为单网盘（夸克）可用；桌面端不出 Linux 包，Linux 请用 Compose 的 aria2 profile。
